# 03 字段抽取与页码定位

## 一、为什么"定位"比"抽取"更重要

核对结论的价值全在"能不能指回原件"：`不一致：批号 — 提单第 1 页第 17 行写 MEG2605-B11，装箱单第 1 页第 23 行写 MEG2605-B12`。
一条没有定位的结论，业务人员无法复核，供应商也不会认。
所以本技能的产出物里，**每个字段值都必须带 `page`（页码）与 `line`（行号）与 `snippet`（原文片段）**。

## 二、三种文件的定位口径

| 文件类型 | 定位口径 | 获取方式 |
|---|---|---|
| PDF | 真实渲染页码 + 该页文本行序号（从上往下 1,2,3…） | `scripts/pdf_text.py` 直接解析内容流，取 `(page, [(y, text)…])` |
| DOCX/XLSX | **先转 PDF、再用 PDF 的页码与行序**；不要用 Word 的"段号"充当页码 | `libreoffice --convert-to pdf`，再按 PDF 口径取 |
| 图片/扫描件 | 页码 = 图片页序；行号 = OCR 文本行序（来自 `<同名>.ocr.txt`） | OCR 全文旁挂文件，必须在看板上注明"OCR 识别，未见原件" |

> 常见错误：直接把 DOCX 的段落序号当页码写进报告（"第 36 段"），业务人员翻不到。
> 也不要把 Excel 的"行 23"写成"页 23"。

## 三、`extract_fields.py` 的工作方式（也是人工复核的检查表）

1. **读文本**：PDF 走 `pdf_text`；DOCX 拍平成"每段一行"（表格单元格用 `~` 连接）；XLSX 每行输出 `A=值 | B=值 | C#=公式`；图片必须配 `.ocr.txt`。
2. **分类**：按 `references/01` 的强/弱特征打分。
3. **取字段**：`RULES[字段] = (锚点正则, 取值模板, 校验器)`，按以下顺序尝试：
   - 锚点与值在**同一行**（`INVOICE NO.: ALN-INV-26-0518`）→ 最可信；
   - 同一**分段**（用 `\t | ; ~` 切分后的下一段）；
   - **下一行/下两行**（表格竖排：标签一行、值一行）→ 要求"整段就是一个完整值"，防止从 `200.000 MT` 里只抠出 `200`；
   - **表头列回填**（DOCX 表格被拍平成"表头一排 + 数据一排"）→ 列名必须与字段语义匹配（`CAS`、`HS`、`UNIT PRICE`…）。
4. **校验器**：`v_hs` 必须 10 位数字且章号在白名单；`v_cas` 校验位算法；`v_money`/`v_qty`/`v_weight` 范围；`v_party` 必须含 CO./LTD/COMPANY 等字样且 ≥2 个大写词；`v_incoterm` 只允许 11 种术语；`v_date` 必须 `YYYY-MM-DD`。
   **校验不过就当没取到**，宁可报 `NOT_FOUND` 也不要把脏值塞进矩阵。

## 四、必须人工复核的 6 种情形

| 情形 | 表现 | 复核动作 |
|---|---|---|
| 表格折行 | PDF 里 `KING ABDULLAH PORT,` / `JUBAIL (SAJUB)` 分两行 | 值取完整语义，`line` 指向**首行**，`snippet` 写清"表格第 X 行" |
| 值由公式汇总 | Excel 合计格为空、由 `=SUM()` 算出 | 定位指向 `TOTAL` 行，并在 `extra` 写明"G14:G22 = 20,000 ×9" |
| 一页多栏 | 双栏排版的合同 | 行号按**视觉行**而非段落序 |
| 同名字段多处出现 | "Payment Terms" 在页脚也出现 | 取**表头上下文**中的那一处（锚点附近 3 行内） |
| 中英混排 | `净重 Net Weight: 180,000 KGS` | 值只取 `180,000`，`snippet` 保留原文 |
| 扫描件 | 倾斜、印章遮盖 | 不猜，标【无法判断】；若必须用，注明 OCR 置信度 |

## 五、定位回查（交付前必跑）

```bash
python scripts/verify_docs.py --fields fields.json --check-locate --docs <单证目录> --pdf-dir <渲染PDF目录>
```

脚本会逐个字段：
1. 打开对应文件（PDF 用渲染 PDF，XLSX 用单元格，图片查 `.ocr.txt`）；
2. 检查该值（或其关键词片段）是否真的出现在登记的页码上；
3. 检查登记的 `line` 那行能否佐证该值；
4. 输出失败清单，**失败必须修到 0 才能出交付物**。

> 允许的"折算"：表格折行时可退化为"片段核对"（值的关键词 ≥ n−1 个出现在该行）。除此之外不接受"大概在这附近"。

## 六、`fields.json` 结构

```json
{
  "batch": {"case_no": "...", "product": "..."},
  "documents": [
    {"file": "05_提单_Bill_of_Lading.png", "type": "BILL_OF_LADING",
     "fields": {
       "bl_no":   {"value": "MEDUHUB0618825", "page": 1, "line": 3,  "snippet": "B/L No. MEDUHUB0618825"},
       "batch":   {"value": "MEG2605-B11",    "page": 1, "line": 17, "snippet": "BATCH NO. MEG2605-B11 ..."},
       "net_weight": {"value": "180,000", "page": 1, "line": 17, "snippet": "NET WT 180,000 KGS"}
     }}
  ]
}
```

- `value` 写"单证上看到的原值"（保留千分位与单位），归一化由引擎做；
- `extra` 可选，用于补充证据（合计口径、公式来源）；
- 字段名必须用 `verify_docs.py` 里的 41 个标准名，否则不参与比对。

## 七、OCR 旁挂文件规范

```
05_提单_Bill_of_Lading.png
05_提单_Bill_of_Lading.ocr.txt     ← 逐行文本，行序 = 视觉行序
```

- 首行写 `【模拟单证 · SIMULATED DOCUMENT】` 或（真实业务）写 `OCR: engine, confidence`；
- 行数不必与原图严格等长，但**关键字段所在的行号**必须与报告一致；
- 不要 OCR 后就丢掉原图：看板左栏仍然展示原图，供人工"两看一印证"。
