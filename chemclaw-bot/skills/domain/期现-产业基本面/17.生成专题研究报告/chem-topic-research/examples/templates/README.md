# 模板与样例

## 文件

| 文件 | 用途 |
| --- | --- |
| `提纲样例_管理层.md` | 5 章，结论前置 + 决策含义 |
| `提纲样例_销售.md` | 6 章，价格坐标 + 压价理由核查 + 报价建议 |
| `提纲样例_采购.md` | 6 章，成本支撑位 + 议价窗口 + 触发信号 |
| `提纲样例_rnd.md` | 6 章，工艺图谱 + 成本差 + 替代边界 |
| `提纲样例_产业研究员.md` | 见 `../soda-ash-2026/交付物/*_研究提纲_已确认.md` |

这些文件都是**工具生成**的，不是手写：

```bash
python scripts/build_md.py outline case.json --audience sales --out 提纲_sales.md
python scripts/build_md.py outline case.json --audience sales --status confirmed --out 提纲_sales_已确认.md
```

## 怎么用

1. 复制最接近你受众的那份，作为**给用户确认的提纲**。
2. 用户确认后，把确认内容回写进 `case.json` 的 `audience_frameworks.<受众>.chapters`。
3. 用 `--status confirmed` 重新生成，作为归档件。

## 提纲的合格标准

- 每章都有：要回答的问题、为什么需要这一章、验证/证伪什么、依赖数据、方法。
- 章节之间存在递进关系，不是并列堆砌。
- 总数 5–10 章（管理层 5–7，研究员 8–10）。
- 用户能一眼看出"这份提纲为什么这样排"。

## 一份提纲的开头长什么样

```markdown
# 中国纯碱行业新增产能对未来供应格局的影响｜研究提纲（待确认）

| 项目 | 内容 |
| --- | --- |
| 受众 | 销售（sales） |
| 研究范围 | 2026Q4 – 2027Q4 |
| 数据截止 | 2026-09-25 |
| 状态 | **待确认：请逐章确认、增删或调整顺序后再开始研究** |

## 一、这一版提纲为谁写
面向销售的专题研究框架：回答"供给变多会不会让客户压价、哪个区域先松动、我该怎么报价与备货"……

## 二、要回答的核心问题
| # | 问题 | 为什么问 | 检索方向 |

## 四、章节设计（每章都写清：为什么存在 / 要验证什么 / 依赖哪些数据）
### 01 现在什么价、在历史上什么位置
- **要回答的问题**：……
- **为什么需要这一章**：……
- **它要验证/证伪什么**：……
- **依赖数据**：……
- **方法**：……
```

**注意"待确认"这一行不能省**——它是流程上一个真实的停顿点，用户看到它才知道可以改。
