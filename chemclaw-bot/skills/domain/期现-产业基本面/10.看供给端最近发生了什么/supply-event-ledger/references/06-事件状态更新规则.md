# 06 · 事件状态更新规则

一条事件不是"登记完就结束"，它有**生命周期**。状态维护得好，台账才有研究价值；维护得差，三个月后就是一堆过期结论。

---

## 事件状态机

```
                 ┌──────────────┐
                 │  已披露计划   │  planned（未发生）
                 └──────┬───────┘
                        │ 实际执行
                        ▼
   ┌────────────┐   停车/检修   ┌──────────────┐
   │   运行中   │ ────────────▶│   停车中     │
   └────────────┘              └──────┬───────┘
          ▲                           │ 重启/开车
          │                           ▼
          │                    ┌──────────────┐
          └────────────────────│  重启/恢复中  │
             产出合格品/满负荷   └──────────────┘
                                       │ 未成功
                                       ▼
                               ┌──────────────┐
                               │  反复/再次停  │
                               └──────────────┘
```

### `status_latest` 标准值

| 值 | 含义 | 使用条件 |
|---|---|---|
| `计划中` | 仅公告，未执行 | 只出现在 planned_events |
| `停车中` | 已停，未重启 | 有明确的"停车/检修"表述，且无后续重启记录 |
| `重启中` | 已开车但未满负荷 | 有"重启中/恢复中/负荷提升中"表述 |
| `已复产` | 恢复正常运行 | 有"运行平稳/正常生产/满负荷"表述 |
| `检修中（预计X）` | 在检修，有时间预期 | 有"预计9月23日重启"类表述 |
| `持续停车（无计划）` | 长期停车 | 有"恢复时间待定/暂无重启计划"表述 |
| `负荷下降` | 未停但降负荷 | 有具体负荷值 |
| `已投料试车` | 新装置试车 | 有"投料/试车/打通流程"表述 |

## 状态更新三原则

### 原则 1：只前进不回退，除非有明确证据

```
8/14 计划8/31停车   → status: 计划中
9/03 计划9/4停车    → status: 计划中（日期修正）
9/16 9/4已停车      → status: 停车中
10/16 运行平稳      → status: 已复产
```

如果 10/16 又出现"停车"，那不是回退，是**第二次事件**（若时间不重叠则建立新 `event_id`）。

### 原则 2：状态变化必须带证据日期

```json
{
  "status_latest": "已复产",
  "status_evidence_date": "2026-10-16",
  "status_note": "9/4如期停车检修…10/16 生意社确认一期运行平稳"
}
```

`status_evidence_date` 是**最后一次确认该状态的来源日期**。没有它，就不知道这条状态是不是一个月前的。

### 原则 3：状态矛盾时，以更具体、更晚的来源为准

```
10/13 隆众汇总表：榆林凯越 9月4日停车检修，为期25天（表格本期未更新）
10/16 生意社    ：凯越装置重启中，负荷提升，预计10月初产出
```

→ 取 **"重启中"**。理由：汇总表是周期性转载（可能滞后），专条报道是最新实地信息。
处理方式：`status_latest="重启中"`，并在 `conflict` 里写明"隆众汇总表为重复引用9月数据，取10/16专条"。

## 如何判定"已复产"

这是最容易过度乐观的地方。三个层级，严格区分：

| 表述 | 判定 | 可否认为供应恢复 |
|---|---|---|
| "重启中" / "开车中" / "负荷提升中" | `重启中` | ❌ 部分恢复 |
| "已产出合格品" | `重启中`（接近满负荷） | ⚠️ 基本恢复 |
| "运行平稳" / "正常生产" / "满负荷运行" | `已复产` | ✅ 是 |
| "计划重启" / "预计X日重启" | 仍是 `停车中` | ❌ 未恢复 |

**典型判例 · 凯越 70 万吨**：

```
9/04 停车检修
9/28 "目前重启中，预计10月初产出产品"
10/13 隆众汇总表仍写"9月4日停车检修，为期25天"
10/16 "装置重启中，负荷逐步提升"
```

→ `status_latest = "重启中"`，`end_date = 2026-10-20`（窗口末日，未确认满负荷）。
**不能**因为"9月4日+25天=9月29日已到期"就判定复产。检修超期是常态。

## 如何处理"反复"

```
10/10 久泰托县 200 万吨停车检修 10-15 天
（期间若出现"重启后又停"）
```

→ 若两次停车时间**不重叠**，且间隔超过恢复验证期（约 7 天），视为两次事件，新建 `event_id`，`event_family` 加后缀（如 `"久泰10月检修"` / `"久泰10月二次停车"`）。
若间隔小于 7 天，视为同一事件的反复，合并并更新 `status_note`。

---

## 事件关闭条件

一条已发生事件在下列情况下可以"关闭"（不再需要跟踪）：

- `status_latest = 已复产` 且 `status_evidence_date` 晚于 `end_date`
- 或窗口已结束且事件在窗口内完整发生

未关闭的事件必须在报告的"数据缺口"里列出，注明**为什么还没关**：

```
E-005 久泰托县 200 万吨：10/10 停车，预计 10-15 天，截至 10/20 无复产确认
      → 影响量按窗口末日计算，实际可能更高（若继续停车）
E-002 新奥二期 60 万吨：7/1 停车至今，恢复时间未定
      → 影响量随停车时长线性增长，每多停 10 天增加 16,438 吨
```

**"每多停 10 天增加多少吨"这个换算，是给研究员最实用的信息。**

## 状态维护节奏

| 频率 | 动作 |
|---|---|
| 每日 | 抓取装置快讯（100ppi 情报 / 化销网），更新 `status_latest` |
| 每周 | 对照隆众/金联创大区装置表，补齐遗漏装置 |
| 每月 | 全量重算 `calc_impact.py`，重新生成 HTML/Excel |
| 季末 | 关闭已完成事件，把未发生事项从 planned 挪到 status_events（若已执行） |

### 版本记录

建议在 `datum.json` 里维护：

```json
"revision": {
  "version": "v3",
  "updated_at": "2026-10-20T18:00:00",
  "changes": [
    "新增 E-031 伊朗Kimiya停车确认",
    "E-003 凯越状态由停车中更新为重启中",
    "E-013 中煤鄂能化降级为待核（无停车证据）"
  ]
}
```

这样每个交付物都能说清"这份报告对应哪一版数据"。

## 状态更新常见错误

| 错误 | 后果 | 纠正 |
|---|---|---|
| 把"计划重启"当成"已重启" | 高估恢复供应 | 计划语态一律不算恢复 |
| 用"检修期已满"推断复产 | 高估恢复供应 | 必须有"运行平稳"类确认 |
| 汇总表未更新就用它的状态 | 状态滞后 | 专条优先于汇总表 |
| 状态更新但没更新 `source_count` | 来源数失真 | 新来源必须追加进 `sources[]` |
| 状态矛盾不记录 | 后续无法追溯 | 写入 `conflict` |
| 已复产事件不关闭 | 台账膨胀 | 按关闭条件归档 |
