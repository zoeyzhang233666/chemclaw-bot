# 销售时点判定

`销售时点` 是这份交付最直接的用处：把"什么时候打电话"从感觉变成规则。判定全部由 `b2bctl merge` 自动完成，规则如下。

## 1. 三个桶

| 桶 | 含义 | 行动 |
|---|---|---|
| `现在就该联系` | 采购决策正在发生，或供应商名单还在调整 | 本周内首通电话 |
| `3-6个月后再联系` | 需求已在路上但采购未启动 | 现在留资/送样/建技术对接，3~6 个月后推商务 |
| `仅需关注` | 尚未形成当期需求，或有取消/延期风险 | 只做商机储备，不投入销售资源 |

## 2. 规则表

以 `today` 为基准，`now_cutoff = today + 3 个月`，`win_cutoff = today + window_months`（按月粒度）。

| 建设阶段 | 预计投产时间 | 判定 | 理由 |
|---|---|---|---|
| `试车` | 任意 | **现在就该联系** | 装置正在消化原料，供应商名单尚可切入，是最佳窗口 |
| `已投产` | 近 6 个月内 | **现在就该联系** | 达产爬坡 + 供应商调整期，补量/换源机会大 |
| `已投产` | 更早 | 仅需关注 | 供应商格局稳定，只作长期替换储备 |
| `在建` | ≤ `now_cutoff` | **现在就该联系** | 装置提前 1~3 个月锁定原料并完成合格供应商入库，决策正在发生 |
| `在建` | `now_cutoff` ~ `win_cutoff` | 3-6个月后再联系 | 采购启动点落在窗口后半段 |
| `在建` | **未披露** | **3-6个月后再联系** | 见下方说明 |
| `在建` | > `win_cutoff` | 仅需关注 | 超出窗口 |
| `备案` | ≤ `win_cutoff` | 3-6个月后再联系 | 落地确定性较高但采购未启动，先建联 |
| `备案` | 其它 | 仅需关注 | 尚未形成当期原料需求 |
| `拟建` / 未披露 | 任意 | 仅需关注 | 有取消或延期风险，仅作商机储备 |

## 3. 为什么「在建 + 未披露投产时间」是 3~6 个月，而不是"仅需关注"

这是本方法论里一个**反直觉但重要**的判定，来自实战：

公开渠道里 **预计投产时间缺失极其普遍**（纯碱华东那一轮：93 条公告来源里有 73 条投产时间未披露）。如果按"没有时间 → 什么都不用做"处理，三个桶会塌成 `16 / 0 / 77`——**"仅需关注"占了 3/4，这张表就没有行动价值了**。

但在建项目**必然**会经历：
1. 技术对接与规格确认（含量/粒度/水分/包装）
2. 合格供应商入库（多数企业的供应商准入流程）
3. 送样检测与小批量试用

这三件事合计通常要 **1~3 个月**，而且**必须在装置投料/点火之前完成**——等到试车再切进去，供应关系往往已经定了。

所以：**在建 + 未披露投产时间 → 归入「3-6个月后再联系」**，理由是"应在未来 3~6 个月完成技术对接与入库，待投产时间明确后立即推进商务"。改这条规则后分布变成 `16 / 43 / 44`——前两个桶合起来 59 条，表开始有用了。

**这条规则可以被产品/行业特性覆盖**：如果某产品的供应商切换周期很长（如需要长周期认证的领域），应该把前置期设得更长。改 `lib/common.py` 的 `derive_timing()` 即可。

## 4. 时间解析

`parse_month()` 能吃下这些写法：

| 写法 | 解析为 |
|---|---|
| `2027-03` / `2027/3` / `2027.3` / `2027年3月` | 2027-03 |
| `2027Q1` | 2027-01 |
| `2027年上半年` / `2027下半年` | 2027-01 / 2027-07 |
| `2027` | 2027-06（**按年中，粗糙**） |
| 其它 | 未披露 |

**注意**：只给年份时取年中，可能把"2027 年底"判成 2027-06，从而被算进窗口。**当线索的关键时间只有年份时，`置信度` 不应给「高」**。

## 5. 建设阶段的坑

- **环评受理 / 拟审批 / 批复 → 一律 `备案`**，不要写成"在建"。环评公示只证明项目在审批流程里，不证明已开工。少数情况正文写明已开工，那才写 `在建`。
- **"投产" 依赖上下文**：`拟投产时间` 是计划，`已投产` 是事实。公告里"预计 2027 年 6 月投产"→ 阶段是在建（或备案），投产时间是 2027-06。
- **技改/扩建 ≠ 新建**：技改项目（如冷修技改、池窑拉丝技改）**也会新增需求**，但常是**一次性集中采购**（点火期整批拿货）而非稳态月均。这类要在 `规模线索` 或 `需求点` 里写明"冷修点火期一次性整批采购量高于稳态月均"。

## 6. 同一条产线被多次披露时

同一个窑炉/装置的"方案调整公告"和一年后的"产能变更公告"是**同一个项目**。判定方法：**比对厂址与产线名称**。如果一致，只保留**最新、信息最全**的一条——否则会重复计数，把一条产线算成两条需求。

纯碱那一轮的真实例子：某玻纤集团桐乡池窑，2025-08 的"年产 12 万吨…冷修技改项目方案调整"与 2026-08 的"18→20 万吨"是**同一条产线**（地址相同，产能先 20→18 后 18→20），只保留后者。

## 7. 自检

```bash
python scripts/b2bctl.py merge <项目目录>
```

看 `merge_stats.json → by_timing`：

- 某个桶为 **0** → 很可能是 `预计投产时间` 大面积缺失，或时间解析失败（检查 `建设阶段` 是否被写成自由文本）。
- `仅需关注` 占比 **> 80%** → 同上，回到本节第 3 节。
- `试车` 桶有值但"现在就该联系"里没有它 → 规则没生效，检查 `norm_stage()` 是否吞掉了"试生产"这类写法。
